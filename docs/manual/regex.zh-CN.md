# 正则

正则测试器用于在把模式写入重写、脚本或其他匹配逻辑前，先用示例文本验证表达式。它能显示完整匹配、捕获组和无匹配状态，减少直接在真实流量上试错的风险。

## 测试器的组成

- **Source Text**：输入待匹配的示例文本。
- **Regular Expression**：输入正则模式。
- **Matches**：查看每个完整匹配及其捕获组。
- **Guide**：打开内置的正则使用说明。

结果会随着输入变化重新计算。模式非法时，测试器会显示错误而不是把错误表达式当成没有匹配。

## 一个最小流程

1. 先准备一段尽量接近真实 Header、URL 或 Body 的脱敏文本。
2. 输入最小可读的模式，例如 `user_id=([0-9]+)`。
3. 检查完整匹配是否覆盖了预期范围。
4. 检查捕获组是否只包含后续动作需要的值。
5. 用包含边界条件的第二段文本再次验证。

示例：

```text
source:  user_id=42&region=cn
pattern: user_id=([0-9]+)
full match: user_id=42
group 1: 42
```

## 编写匹配规则时的建议

- 能用固定 Host、Path 或 Method 限定范围时，不要把所有条件都塞进一个复杂正则。
- 给分组加上明确边界，避免 `.*` 吞掉后续字段。
- 分别测试空值、换行、大小写、重复字段和特殊字符。
- 用脱敏样本测试 Cookie、Token 和个人信息，不要把生产数据直接复制进手册或共享记录。
- 测试器通过不代表 Rewrite 动作一定成功；最终还要在真实但可控的测试请求上验证编码和上下文。

## 常见问题

### 没有匹配

确认输入文本确实包含目标内容，检查大小写、换行和转义字符。若模式来自 JSON 或脚本字符串，还要额外检查字符串转义是否改变了表达式。

### 匹配太多

缩小匹配范围，增加 Host、字段名或分隔符上下文，尽量使用明确字符集和非贪婪量词。

### 捕获组不符合预期

区分“完整匹配”和“捕获组”。只有带括号的分组才会出现在组结果中；不需要返回值的括号可以改成非捕获组（如果当前运行时支持）。
