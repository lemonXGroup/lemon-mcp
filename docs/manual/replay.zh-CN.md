# 重放

重放用于保存一个可编辑的 HTTP 请求，并在之后再次执行。它适合复现接口问题、比较请求参数变化后的响应，或验证一个 Rewrite / Hosts 配置是否达到预期。

## 重放和重新操作 App 的区别

重新操作 App 会同时受到界面状态、登录状态、时间和其他请求的影响；重放只执行你保存的那一个请求，因此更容易建立可重复的实验。但它也可能绕过客户端原本的业务流程，不能直接等同于一次完整的用户操作。

## 创建重放

可以从空白项目创建，也可以以已知请求为基础整理出一个重放项目。编辑页包含：

| 字段 | 说明 |
| --- | --- |
| Name | 用于识别实验目的的名称 |
| URL | 完整的目标地址，必须包含合法 Host |
| Headers | 请求需要的 Header；删除不必要的认证或追踪字段 |
| Method | HTTP 方法 |
| Request Body | 请求正文，编辑器会根据内容提供相应预览 |

保存前先确认 URL、方法和 Body 的对应关系。例如 GET 通常不需要 Body，而带 JSON Body 的 POST 需要同步设置正确的 Content-Type。

## 执行与结果

列表中的播放按钮会执行保存的请求；执行中可以取消。单条重放完成后，列表会保留最近状态码，详情页可以查看响应预览。创建、保存和执行是不同动作：保存成功不代表服务端已经收到请求，执行完成也不代表业务操作一定成功。

建议每次只改变一个变量：

1. 先保存原始请求并执行一次，记录状态码与关键响应字段。
2. 只修改一个 Header、参数或 Body 字段。
3. 再次执行并比较响应。
4. 将结论和目标环境记录在名称或外部测试记录中。

## 适合的场景

- 验证服务端对边界参数的处理。
- 对比不同 Authorization、Header 或 Body 的响应。
- 在添加 Rewrite 后，确认同一请求是否得到预期结果。
- 复现一次偶发请求，减少手工操作带来的变量。

## 风险与清理

重放是真实的网络请求，不是离线预览。它可能创建数据、修改状态、触发支付或发送通知。执行前确认：

- URL 指向测试环境，或你明确知道生产环境的影响。
- Cookie、Authorization、幂等键和时间戳仍然有效。
- 请求是否会产生不可逆副作用。
- 不再需要时删除包含 Token、个人数据和敏感 Body 的重放项目。

如果请求依赖短期签名、Nonce 或服务端会话，保存的重放可能返回认证失败。这是请求上下文已经变化，而不是重放功能一定失败。
